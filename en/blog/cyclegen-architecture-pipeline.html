CycleGen — driving cycles from a map

CycleGen produces a speed and grade profile from a real route, then a force balance at the wheels. It is not regulatory homologation: it is a chain of map → limits along the road → driver → vehicle, with the demo right here in this page.

Try it in the page Code on GitHub

What it is for

Early in a vehicle program (energy, braking, mountain driving), you want cycles tied to real geography — not just a flat regulatory cycle. CycleGen chains the steps: plot a route, build a speed envelope along the distance, have a driver model “drive” under that envelope, then translate acceleration into forces, torque and power at the wheels.

The web screen is a workbench (map, sliders, charts). The physics runs on a Python server — deliberately outside the browser.

Two cadences

Rebuilding the geometry (route, elevation, traffic lights) is expensive: network calls, digital elevation models. Changing the driving style or the vehicle, once the corridor is in memory, is cheap — a few tens of milliseconds.

Product rule: rebuilding the corridor is an explicit action; tweaking the driver is a fast re-simulation, without resetting the map.

Pipeline (expensive vs cheap)

Driver

A classic controller acting on speed error chases a setpoint and often oscillates on a hilly road. CycleGen uses a continuous driver model (Intelligent Driver Model): at each step, an acceleration that balances “I want to go this fast” against “I keep a safe distance”. Eco / Normal / Sport only change a few knobs (max acceleration, comfortable braking, speed factor) — not a different physics.

A small optional noise term simulates jitter in free driving; it is switched off as soon as the driver brakes hard or a hazard is too close.

Equations and code — driver

IDM acceleration and desired gap \(s^*\) (\(a_{\max}\) desired acceleration, \(b_{\mathrm{comf}}\) comfortable braking, \(T\) time headway, \(s_0\) standstill gap):

\[ a_{\mathrm{IDM}}=a_{\max}\left( 1-\left(\frac{v}{v_0}\right)^{\delta} -\left(\frac{s^{*}}{s}\right)^{2} \right) \quad(\delta=4) \] \[ s^{*}=s_0+v\,T+\frac{v\,\Delta v}{2\sqrt{a_{\max}\,b_{\mathrm{comf}}}} \] \[ v_0=\max\bigl(0{,}1,\; V_{\mathrm{envelope}}(s)\cdot \texttt{speed\_factor}\bigr) \]

Noise cut-off and clipping, then Euler integration (\(\Delta t\approx 1\,\mathrm{s}\)):

\[ d_{\mathrm{brake}}=\max\!\Bigl(\frac{v^{2}}{2\,b_{\mathrm{comf}}},\,25\Bigr)\quad[\mathrm{m}] \] \[ a=\operatorname{clip}\bigl(a_{\mathrm{IDM}}+a_{\mathrm{noise}},\; -1{,}5\,b_{\mathrm{comf}},\; a_{\max}\bigr) \] \[ v\leftarrow v+a\,\Delta t,\qquad s\leftarrow s+v_{\mathrm{old}}\,\Delta t \] 
# Excerpt — a_IDM (kinematic_solver.py)
free = 1.0 - (v / v0) ** DELTA
dv = v - v_lead
s_star = params.s0 + max(
    0.0,
    v * params.T
    + (v * dv) / (2.0 * math.sqrt(max(params.a_max * params.b_comf, 1e-6))),
)
return params.a_max * (free - (s_star / gap) ** 2)

Corridor

Before driving, we prepare what lies along the road: grade, speed limits, a traffic estimate when available, comfortable cornering speed. The resulting envelope is the minimum of these limits. Raw elevation sometimes dips under a bridge: we correct for map structures, smooth, then compute the grade. Shown in % on screen; computed in radians.

Equations — corridor and envelope

Object indexed by distance \(s\):

\[ \bigl(S,\;\alpha(s),\;V_{\mathrm{legal}},\;V_{\mathrm{traffic}},\;V_{\mathrm{curve}},\;V_{\mathrm{envelope}},\;S_{\mathrm{feux}}\bigr) \]

Grade after smoothing (Savitzky–Golay, denoted SG):

\[ \alpha_i=\operatorname{atan}\!\left(\frac{z^{\mathrm{SG}}_i-z^{\mathrm{SG}}_{i-1}}{S_i-S_{i-1}}\right) \]

Cornering (\(a_y\) lateral comfort, \(R\) radius) and envelope:

\[ V_{\mathrm{curve}}(s)=\sqrt{a_y\,R(s)} \] \[ V_{\mathrm{envelope}}(s)=\min\bigl(V_{\mathrm{legal}}(s),\,V_{\mathrm{traffic}}(s),\,V_{\mathrm{curve}}(s)\bigr) \]

Forces at the wheels

The driver proposes an acceleration. The vehicle model bounds what traction and brakes can actually deliver: road load (coefficients F0, F1, F2), the grade component, then the applied force limited by power and maximum braking. We reconstruct the actual acceleration, then torque and power at the wheels.

The demo catalog offers ballpark figures for electric vehicles (unofficial). For a critical study, substitute manufacturer data or authorized measurements.

Equations and code — force balance \[ F_{\mathrm{need}}=m\,a_{\mathrm{cmd}}+F_{\mathrm{road}}+F_{\mathrm{grade}} \] \[ F_{\mathrm{road}}=F_0+F_1\,v_{\mathrm{km/h}}+F_2\,v_{\mathrm{km/h}}^{2},\qquad F_{\mathrm{grade}}=m\,g\,\sin\alpha \] \[ a=\frac{F_{\mathrm{applied}}-F_{\mathrm{road}}-F_{\mathrm{grade}}}{m} \] \[ T=F\,r_{\mathrm{dyn}},\qquad P=T\,\omega \] 
# Road-load (kinematic_solver.py)
def _road_load_n(v_mps: float, plant: VehiclePlant) -> float:
    vk = max(0.0, v_mps) * 3.6  # m/s → km/h
    return plant.f0_n + plant.f1_n_per_kph * vk + plant.f2_n_per_kph2 * vk * vk

Alpine roads

To stress braking and downhill speed control, the demo ships with pre-filled packs (Pico Veleta, Grossglockner, Iseran, Stelvio): geometry, corridor, first profile. On opening, all four screens (Route → Constraints → Driver → Cycle) are populated. Re-running a live generation goes through the compute server.

Reading the screen

One main chart (usually speed), a strip of thumbnails to switch quantities, a shared cursor between map ↔ curves. The idea: look at the phenomenon (envelope tracking, torque peak), not rearrange nine panels.

Stack and limitations

Static front end (Next.js) on GitHub Pages; Python compute (FastAPI) in a container, currently on Render — a cold start is possible after inactivity. CycleGen is not a field test campaign, nor homologation, nor a detailed thermal model of the battery or brakes. Cornering speed is a lateral comfort limit, not the tire grip limit.
