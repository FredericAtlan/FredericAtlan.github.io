CycleGen — architecture et physique : du corridor à la force aux roues

CycleGen génère des profils \(v(t)\), \(\alpha(t)\) et bilans mécaniques à partir d’un trajet cartographique. Ce n’est pas un jumeau de contrôleur batterie, ni une homologation WLTP : c’est une chaîne itinéraire → enveloppe spatiale → conducteur IDM → plant véhicule, avec métadonnées d’audit et code open source.

Ce que ce rapport démontre

  • Modélisation conducteur IDM continu (vs PID oscillant) + gate Markov en freinage dur.
  • Géospatial → physique DEM / ponts OSM, \(V_{curve}\), \(V_{envelope}\), road-load \(F_0,F_1,F_2\).
  • Architecture Thin routers FastAPI ; vérité dans kinematic_solver ; pas d’IDM dans React.
  • UI ingénierie Focus + contexte (graphe principal, sparklines, carte sync playhead).

0. Abstract

En ingénierie amont (énergie, freinage, scénarios alpins), on a besoin de cycles géographiques reproductibles. CycleGen orchestre : routage (HERE / Mapbox / OSRM) → corridor spatial \(V_{envelope}(s)\) → POST /api/simulate/start → IDMSolver (+ plant véhicule) → profil consolidé exportable. Le frontend Next.js est un atelier ; la physique vit côté Python.

1. Architecture : frontières cheap / expensive

Règle produit (et de perf) : rebuild corridor (routeurs, DEM, feux) = action utilisateur explicite ; update dynamics (params IDM / véhicule) = re-sim debounce 50–100 ms via l’API, sans logique métier dans React. 

Wizard (CycleGenShell)
  → frontend/src/lib/api.ts
      POST /api/route/analyze      # expensive
      POST /api/corridor/build     # expensive
      POST /api/simulate/start     # cheap re-run si corridor en mémoire
  → FastAPI thin routers
  → spatial_processor → SpatialCorridor
  → simulation_manager → kinematic_solver.IDMSolver
  → frames / ConsolidatedProfile (+ WS optionnel)

Contrats Pydantic, stores TTL, caps DoS sur Overpass / fingerprint. Auth optionnelle CYCLEGEN_API_KEY. Sur GitHub Pages : NEXT_PUBLIC_API_MODE=direct vers l’API hébergée (Render).

2. L’adieu au PID : l’Intelligent Driver Model

Une boucle PID sur l’erreur de vitesse produit souvent des micro-oscillations et des réactions « tout ou rien ». L’IDM calcule une accélération continue à partir de grandeurs conducteur (désirée, gap, confort) :

\[ a_{\mathrm{IDM}}=a_{\max}\left( 1-\left(\frac{v}{v_0}\right)^{\delta} -\left(\frac{s^{*}}{s}\right)^{2} \right) \quad(\delta=4) \] \[ s^{*}=s_0+v\,T+\frac{v\,\Delta v}{2\sqrt{a_{\max}\,b_{\mathrm{comf}}}} \] \[ v_0=\max\bigl(0{,}1,\; V_{\mathrm{envelope}}(s)\cdot \texttt{speed\_factor}\bigr) \]

Profils Eco / Normal / Sport (et calibrages Route Studio) ne changent que \(a_{\max}\), \(b_{\mathrm{comf}}\), \(T\), \(s_0\), speed_factor — pas une autre physique. Un bruit Markov optionnel est coupé dès que \(a_{\mathrm{IDM}}\le -1\,\mathrm{m/s^2}\) ou qu’un danger est dans l’horizon de freinage : la nervosité en roulage libre ne pollue pas un arrêt d’urgence. 

# backend/app/services/kinematic_solver.py — _idm_accel
free = 1.0 - (v / v0) ** DELTA
dv = v - v_lead
s_star = params.s0 + max(
    0.0,
    v * params.T
    + (v * dv) / (2.0 * math.sqrt(max(params.a_max * params.b_comf, 1e-6))),
)
return params.a_max * (free - (s_star / gap) ** 2)

3. Corridor spatial : topographie sans « plongeon » sous les ponts

Le solveur micro a besoin d’un objet échantillonnable le long de l’abscisse curviligne \(s\) :

\[ \bigl(S,\;\alpha(s),\;V_{\mathrm{legal}},\;V_{\mathrm{traffic}},\;V_{\mathrm{curve}},\;V_{\mathrm{envelope}},\;S_{\mathrm{feux}}\bigr) \]

Les DEM bruts mettent souvent le sol de la vallée sous un pont. CycleGen interpole \(z\) entre les extrémités de structure OSM (pont / tunnel), lisse (Savitzky–Golay), puis :

\[ \alpha_i=\operatorname{atan}\!\left(\frac{z^{\mathrm{SG}}_i-z^{\mathrm{SG}}_{i-1}}{S_i-S_{i-1}}\right) \]

Affichage % = \(100\cdot\tan\alpha\) (UI seule) ; stockage solveur en radians. Courbure → vitesse latérale de confort :

\[ V_{\mathrm{curve}}(s)=\sqrt{a_y\,R(s)},\qquad V_{\mathrm{envelope}}=\min\bigl(V_{\mathrm{legal}},\,V_{\mathrm{traffic}},\,V_{\mathrm{curve}}\bigr) \]

(\(a_y\) défaut \(2{,}5\,\mathrm{m/s^2}\).) C’est cette enveloppe — pas une consigne PID — qui borne \(v_0\) de l’IDM. Côté UI Contraintes : sources Z (HERE / Open-Meteo / …), filtre spatial (ex. AVL N90), clamp grade, trapèzes \(L\), bornes pente min/max — rebuild corridor = action explicite (« Construire le cycle »).

4. Bilan de forces : road-load et plant véhicule

Une fois \(a_{\mathrm{cmd}}\) issu de l’IDM (éventuellement lissé jerk / pedal lag), le plant véhicule clippe la commande par puissance, couple frein et pente. Forme du bilan longitudinal :

\[ F_{\mathrm{need}}=m\,a_{\mathrm{cmd}}+F_{\mathrm{road}}+F_{\mathrm{grade}} \] \[ F_{\mathrm{road}}=F_0+F_1\,v_{\mathrm{km/h}}+F_2\,v_{\mathrm{km/h}}^{2},\qquad F_{\mathrm{grade}}=m\,g\,\sin\alpha \]

Puis \(F_{\mathrm{applied}}\) est borné par \(P_{\max}/v\) (traction) et \(\tau_{\mathrm{brake}}/r_{\mathrm{dyn}}\) (frein) ; on reconstruit \(a=(F_{\mathrm{applied}}-F_{\mathrm{road}}-F_{\mathrm{grade}})/m\). Couple / puissance aux roues suivent \(T=F\,r_{\mathrm{dyn}}\) et \(P=T\,\omega\). 

# backend/app/services/kinematic_solver.py
def _road_load_n(v_mps: float, plant: VehiclePlant) -> float:
    vk = max(0.0, v_mps) * 3.6
    return plant.f0_n + plant.f1_n_per_kph * vk + plant.f2_n_per_kph2 * vk * vk

# clip_vehicle_accel: f_need = m*a_cmd + f_road + m*g*sin(alpha)
# puis min/max traction & frein → a reconstruit

Catalogue seed démo = proxies BEV d’ingénierie (ordres de grandeur publics, pas des CoC) : Zoé R135, Leaf 40, ID.3 Pro, Model 3 RWD, Ioniq 5, BEV-C-TM générique. Exemple BEV-C-TM : \(m=1810\,\mathrm{kg}\), \(F_0=102\,\mathrm{N}\), \(F_2=0{,}028\), \(r_{\mathrm{dyn}}=0{,}322\,\mathrm{m}\), \(P=150\,\mathrm{kW}\). Les road-loads constructeur (C-Space, X-Space/Grossglockner, BCB) sont retirés du seed public.

La cohérence du bilan (\(F_{\mathrm{trac}}\) vs somme résistances + inertie) se vérifie sur les exports CSV — c’est un test de non-régression numérique, pas une « preuve » que le véhicule réel est cloné.

5. Épreuves alpines : Pico Veleta et Grossglockner

Pour stress-tester freins, retenue et enveloppes en descente / montée longue, la démo embarque des packs HERE pré-enregistrés (geo + corridor + profil) :

  • Pico Veleta (Espagne) — descente / montée asphaltée côté Sierra Nevada ; juge de paix pour effort traction / freinage soutenu et enveloppes \(V_{\mathrm{legal}}\).
  • Grossglockner (Autriche) — descente type Edelweißspitze → fond de vallée, \(\sim 14{,}7\,\mathrm{km}\), pentes fortes ; scénario freinage / retenue.
  • Iseran / Stelvio — mêmes mécaniques, autres géométries (stress freins cols).

Ces packs peuplent les quatre écrans du wizard à l’ouverture (trajet → contraintes → conducteur → cycle), sans attendre un cold start API pour lire un résultat — la re-génération live, elle, passe par simulate/start.

6. UI : Focus + contexte, pas une grille de neuf graphes

Empiler vitesse, \(a\), \(P\), \(\tau\), pente… en neuf panneaux égaux surcharge l’ingénieur. Le poste Cycle (étape 4) suit un paradigme Focus + Contexte :

  • un graphe focus (série primaire, overlays limites / moyenne / RMS) ;
  • un bandeau de miniatures pour basculer V, \(a\), \(P_t\), \(\tau\), … ;
  • un HUD au curseur (valeurs sync à l’instant \(t\)) + audit sécurité (\(\lvert a\rvert_{\max}\), gate Markov, clips) ;
  • un playhead commun carte ↔ courbes ↔ loupe pente / 3D ;
  • ledger applicatif (config / géométrie / résultats) ; pas de corridor passé en URL.

Objectif : passer du temps sur le phénomène physique (suivi d’enveloppe, pics de couple, freinage en descente), pas sur la configuration de l’outil.

7. Livraison

  • Front — Next.js export statique, basePath=/CycleGen, GitHub Pages.
  • API — FastAPI Docker, $PORT, Render free (cyclegen-api.onrender.com) ; cold start possible.
  • Qualité — unittests backend, tsc, Playwright live (smoke Pages + assert catalogue proxies BEV).

8. Limites (explicites)

CycleGen n’est pas une vérité terrain NDS, ni une homologation réglementaire officielle, ni un modèle thermique batterie / frein à disque. \(V_{curve}\) est un confort latéral, pas une limite d’adhérence. Les TPM Markov et seeds sont des proxies d’ingénierie documentés. Les chiffres véhicule ci-dessus sont ceux du catalogue seed open ; toute étude critique doit substituer des CoC / mesures autorisées.
